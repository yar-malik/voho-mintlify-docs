Rime on-prem services expose several endpoints for monitoring the health of a self-hosted deployment. Use them to inform scaling and performance decisions.

## API Container

The API container serves a `/health` route on port 8000 that reports overall status:

```bash
curl -X GET "http://localhost:8000/health"
```

A typical response:

```json
{
  "apiStatus": "ok",
  "timestamp": "2025-04-03T13:59:58.902Z",
  "licenseStatus": "valid",
  "modelReachable": true
}
```

The response confirms that both the API and model services are up and responding.

### Healthcheck

Use `/readyz` for readiness and `/livez` for liveness:

```bash
curl -X GET "http://localhost:8080/readyz"
```

A typical response: `ok`

### Metrics

The model can emit OpenTelemetry metrics, and the internal vLLM process also exposes a Prometheus `/metrics` endpoint; either works as a data source for metrics collection, tuning, and debugging.

#### OpenTelemetry Metrics

The Rime engine exposes the following OpenTelemetry metrics:

- `rime.engine.concurrent_pipeline`
- `rime.engine.generated_audio_duration`
- `rime.engine.gpu_load`
- `rime.engine.initial_latency`
- `rime.engine.invocation_request`
- `rime.engine.unicode_scalar_value_count`
- `rime.engine.stage.items_in`
- `rime.engine.stage.items_out`
- `rime.engine.stage.first_output_latency`

The `rime.engine.stage.*` series carry a `stage` attribute. To have the model emit OpenTelemetry metrics, set two environment variables:

- `OTEL_COLLECTOR_PROTOCOL` — set to `grpc` (recommended), `http/protobuf`, or `http/json`.
- `OTEL_COLLECTOR_ENDPOINT` — provide a valid OpenTelemetry Collector endpoint.

```bash
OTEL_COLLECTOR_PROTOCOL='grpc'
OTEL_COLLECTOR_ENDPOINT="https://${OTELCOL_DOMAIN:?}:4317"
```

<Info>
  The model does not set any resource attributes for these metrics. Use `OTEL_RESOURCE_ATTRIBUTES` to define them. The model does not implement OpenTelemetry authentication. If you need authentication, run an OpenTelemetry Collector sidecar to forward the metrics.
</Info>

#### Prometheus Metrics

To retrieve vLLM Prometheus metrics, issue an HTTP request to `http://localhost:${GENERATOR_SERVICE_PORT:?}/metrics`. By default, a random port is assigned to the vLLM server. To choose a fixed port, set `GENERATOR_SERVICE_PORT` to an available port number. `GENERATOR_VLLM_PORT` is still read as a deprecated fallback when `GENERATOR_SERVICE_PORT` is unset.

#### OpenTelemetry Collector Sidecar

<Tip>
  If you need authentication or other OpenTelemetry Collector extensions, use the `contrib` distribution that includes them.
</Tip>

You can run an OpenTelemetry Collector to forward both the OpenTelemetry and Prometheus metrics, or to retrieve the OpenTelemetry metrics locally. Example Docker Compose configuration:

```yaml
services:
  model:
    image: us-docker.pkg.dev/rime-labs/arcana/v2/en:<tag>
    # ...
    environment:
      # ...
      "GENERATOR_SERVICE_PORT": 30000
      "OTEL_COLLECTOR_PROTOCOL": "grpc"
      "OTEL_COLLECTOR_ENDPOINT": "http://otelcol:4317"
  otelcol:
    image: otel/opentelemetry-collector-contrib:0.139.0
    ports:
      # ...
      - "9090:9090" # Prometheus exporter, for local retrieval on a /metrics endpoint
    volumes:
      - "./otelcol/config.yaml:/etc/otelcol-contrib/config.yaml:ro"
      # ...
```

where `otelcol/config.yaml` is the configuration file for the OpenTelemetry Collector:

```yaml otelcol/config.yaml
receivers:
  # Provide endpoints for OpenTelemetry metrics from the model
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
  # Scrape the vLLM Prometheus /metrics endpoint
  prometheus/generator-vllm:
    config:
      global:
        scrape_interval: "1s"
      scrape_configs:
        - job_name: "generator-vllm"
          static_configs:
            # Assuming GENERATOR_SERVICE_PORT=30000
            - targets: ["model:30000"]
exporters:
  otlp:
    # Consider using the authenticator extension if authentication is required
    endpoint: "another.opentelemetry.collector.example:4317"
  prometheus:
    endpoint: "0.0.0.0:9090"
service:
  pipelines:
    # Forward the OpenTelemetry and Prometheus metrics to another OpenTelemetry Collector endpoint
    metrics/otlp:
      receivers: [otlp, prometheus/generator-vllm]
      exporters: [otlp]
    # Expose the OpenTelemetry and Prometheus metrics locally with another Prometheus /metrics endpoint
    metrics/local:
      receivers: [otlp, prometheus/generator-vllm]
      exporters: [prometheus]
```

#### Histogram Tuning

Metrics that emit histogram data use pre-configured bucket boundaries. These are configurable through `HISTOGRAM_BUCKETS_*` environment variables. To separate differently-tuned sets of data across individual metrics, attach a suffix using `HISTOGRAM_SUFFIX_*` environment variables.

<AccordionGroup>
  <Accordion title="rime.engine.initial_latency">
    - Measured in milliseconds.
    - Default bounds: `0.0, 100.0, 150.0, 200.0, 225.0, 250.0, 275.0, 300.0, 325.0, 350.0, 375.0, 400.0, 450.0, 500.0, 1000.0`
    - Set alternative bounds: `HISTOGRAM_BUCKETS_INITIAL_LATENCY_MS='0.0, 90.0, 95.0, 100.0, 105.0, 110.0, 115.0, 120.0, 125.0, 130.0, 135.0, 140.0, 150.0, 175.0, 200.0'`
    - Set alternative metric name suffix: `HISTOGRAM_SUFFIX_INITIAL_LATENCY='tuned_120ms'` produces `rime.engine.initial_latency.tuned_120ms`
  </Accordion>

  <Accordion title="rime.engine.generated_audio_duration">
    - Measured in seconds.
    - Default bounds: `0.0, 0.5, 1.0, 1.5, 2.0, 2.5, 3.0, 4.0, 5.0, 6.0, 7.5, 10.0, 20.0, 30.0, 60.0`
    - Set alternative bounds: `HISTOGRAM_BUCKETS_GENERATED_AUDIO_DURATION_SECONDS='0.0, 0.5, 1.0, 1.5, 2.0, 2.5, 3.0, 4.0, 5.0, 6.0, 7.5, 10.0, 20.0, 30.0, 60.0'`
    - Set alternative metric name suffix: `HISTOGRAM_SUFFIX_GENERATED_AUDIO_DURATION='tuned_3s'` produces `rime.engine.generated_audio_duration.tuned_3s`
  </Accordion>
</AccordionGroup>

## Mist Container

### Healthcheck

Use the `/livez` and `/readyz` probes on the engine HTTP port:

```bash
curl -X GET "http://localhost:8080/livez"
curl -X GET "http://localhost:8080/readyz"
```

<Note>
  Current Mist images do not serve `/ping`. Use `/livez` for liveness and `/readyz` for readiness.
</Note>

### Metrics

Mist containers do not run a generator service and do not expose a Prometheus endpoint. Export Mist telemetry with the engine's OpenTelemetry exporter (`OTEL_COLLECTOR_PROTOCOL` and `OTEL_COLLECTOR_ENDPOINT`) and convert it to Prometheus in a collector if needed; see the OpenTelemetry Collector sidecar example above.
