Performance tuning applies to both Coda and Arcana on-prem deployments. Tune concurrency against an explicit service-level target. Rime does not provide rate limiting or request queues because those controls depend on the deployment, so enforce the concurrency limit in your own infrastructure.

## What to Measure

- **Initial latency** (TTFF/TTFB): the time from sending a request until the first frame arrives. Lower is better.
- **Real-time factor (RTF)**: processing time divided by stream duration. RTF must remain at or below 1 for real-time delivery. Lower is better.
- **Concurrency**: the number of simultaneous requests the service can handle while meeting the target. Higher is better.

<Note>
  Latency and RTF usually rise with concurrency. Queue or reject requests above the measured limit instead of allowing overload to degrade every active stream.
</Note>

## Coda

For Coda, `GENERATOR_MAX_BATCH` and `INFERENCE_CONCURRENCY_CAPACITY` are the tuning controls, and their defaults work for most deployments. `INFERENCE_CONCURRENCY_CAPACITY` (default `128`) sets the generator's admission limit and sizes its KV cache, so raising it costs GPU memory.

| Variable | Default |
| --- | --- |
| `GENERATOR_MAX_BATCH` | `64` |
| `INFERENCE_CONCURRENCY_CAPACITY` | `128` |

Increase `GENERATOR_MAX_BATCH` to `128` when you serve higher traffic or run on more modern GPUs. A larger batch supports higher concurrency at the cost of longer container startup time.

## Arcana

Arcana exposes additional batching, session, and memory controls. Tune them together against representative traffic.

### Tuning Workflow

Use [`armchair`](https://crates.io/crates/armchair) to repeat this benchmark-driven loop:

<Steps>
  <Step title="Run a baseline">
    Run a baseline without specifying concurrency (`-c`) and set the latency, real-time-factor, and success-rate constraints you need.
  </Step>
  <Step title="Increase batch sizes">
    If RTF is significantly lower than 1, increase both `DECODER_MAX_BATCH` and `GENERATOR_MAX_BATCH`.
  </Step>
  <Step title="Reduce memory utilization">
    If the server fails to start with an out-of-memory error, decrease `GENERATOR_GPU_MEMORY_UTILIZATION`.
  </Step>
  <Step title="Converge">
    Repeat until the benchmarked concurrency converges with `DECODER_MAX_BATCH` and `GENERATOR_MAX_BATCH`. Treat that value as the maximum concurrency for the deployment.
  </Step>
</Steps>

### Controls

These model-container environment variables control batching, sessions, and memory use. Arcana v2 and v3 images ship different defaults:

| Variable | Arcana v2 default | Arcana v3 default |
| --- | --- | --- |
| `DECODER_MAX_BATCH` | `32` | `16` |
| `DECODER_NUM_SESSIONS` | `6` | `6` |
| `GENERATOR_MAX_BATCH` | `32` | `256` |
| `GENERATOR_GPU_MEMORY_UTILIZATION` | `0.8` | `0.8` |
| `GENERATOR_MAX_BATCHED_TOKENS` | not set | `8192` |

<Note>
  The defaults support Rime's lowest supported hardware specification. Higher-capacity hardware should still be tuned against representative traffic rather than a fixed concurrency assumption.
</Note>

### Reference Benchmark

Rime benchmarks with [`armchair`](https://crates.io/crates/armchair):

- Initial latency is measured at one concurrent request (`-c 1`).
- Maximum concurrency requires a 100% success rate, P99 latency at or below one second, and P99 RTF at or below 1 (`--target=success:1.00,ttfb:p99@1s,rtf:p99@1.00`).

| Model | Hardware | Initial latency | Maximum concurrency |
| --- | --- | --- | --- |
| Arcana v2 | H100 | mu=400ms | 32 |

<Info>
  This reference uses `armchair` defaults from the same machine that serves the image, which removes network latency from the measurement. Actual results vary with hardware, software, latency targets, and traffic shape.
</Info>
